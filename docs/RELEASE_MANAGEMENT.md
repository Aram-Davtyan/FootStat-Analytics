# Управление выпуском и сопровождение ИС в условиях версионного контроля

## 1. Цель и область
Документ описывает углубленный процесс выпуска (релиза) и сопровождения ИС с использованием Git,
включая контроль версий, подготовку релизов, тестирование, откаты и поддержку.

## 2. Роли и ответственность
- Разработчик: реализация изменений, локальное тестирование, подготовка MR/PR.
- Ревьюер: проверка кода, архитектурных решений, согласование релиза.
- Ответственный за релиз: формирование версии, выпуск тега, контроль артефактов.
- Сопровождение: обработка дефектов и регресса, выпуск hotfix.

## 3. Базовые принципы
- Все изменения фиксируются в Git и проходят через ветки.
- Релиз возможен только из стабильной ветки `main`.
- Документация актуализируется вместе с функционалом.
- Конфиденциальные данные не попадают в репозиторий.
››
## 4. Стратегия ветвления
- `main` — стабильная версия, соответствует последнему релизу.
- `feature/<topic>` — разработка функционала.
- `fix/<issue>` — исправления дефектов.
- `release/<version>` — подготовка релиза (если нужен отдельный этап).
- `hotfix/<issue>` — экстренные исправления в проде.

## 5. Версионирование
Формат: `MAJOR.MINOR.PATCH`.
- `MAJOR` — несовместимые изменения, требуют обновления инструкции пользователя.
- `MINOR` — новое поведение без ломки.
- `PATCH` — исправления, не меняющие интерфейсы.

Пример: `v1.4.2`.

## 6. Жизненный цикл релиза
### 6.1. Инициация
1. Создать ветку `feature/<topic>` или `release/<version>`.
2. Определить объем релиза (задачи, риски, сроки).

### 6.2. Реализация
1. Код и конфиги изменяются в рамках одной задачи.
2. Коммиты оформляются атомарно и информативно.
3. Обновляются документы в `docs/*`.

### 6.3. Проверка качества
1. Автотесты (при наличии): `vendor/bin/codecept run`.
2. Ручная проверка ключевых сценариев:
   - Поиск игроков.
   - Страница профиля.
   - Загрузка изображения через прокси.
3. Проверка регрессий: сравнение с прошлой стабильной версией.

### 6.4. Подготовка релиза
1. Сводка изменений (release notes).
2. Проверка миграций/конфигов.
3. Финальная сборка из `main`.

### 6.5. Выпуск
1. Слияние в `main`.
2. Тегирование версии: `git tag vX.Y.Z`.
3. Публикация релизных заметок.

## 7. Поддержка и сопровождение
### 7.1. Регистрация дефектов
- Источник: баг-репорт, мониторинг, жалобы пользователя.
- Классификация: критичный / высокий / средний / низкий.

### 7.2. Обработка дефектов
1. Создать ветку `fix/<issue>` или `hotfix/<issue>`.
2. Исправить дефект и покрыть тестом (если база тестов есть).
3. Выпустить `PATCH` релиз.

### 7.3. Регрессия
После исправлений обязательно проверять:
- Поиск игроков.
- Получение профиля.
- Корректность отображения данных.

## 8. Управление изменениями и совместимость
- Перед несовместимыми изменениями обновлять документацию и сценарии.
- Для API-изменений сохранять обратную совместимость или явно фиксировать в release notes.

## 9. Контроль артефактов релиза
Минимальный набор:
- Исходный код в `main`.
- Тег версии `vX.Y.Z`.
- Документация `docs/*`.
- Сводка изменений.

## 10. Откат и восстановление
- Откат возможен через возврат на предыдущий тег.
- При критических сбоях: переключение на последнюю стабильную версию.
- Важные операции (миграции) сопровождаются резервной копией.

## 11. Практики коммитов
Формат:
- `feat: ...` — функционал
- `fix: ...` — исправления
- `docs: ...` — документация
- `refactor: ...` — рефакторинг
- `chore: ...` — технические задачи

## 12. Минимальный регламент сопровождения
- Все изменения проходят через ветки и ревью.
- Документация обязательна для релизов.
- Релиз только из `main`.
